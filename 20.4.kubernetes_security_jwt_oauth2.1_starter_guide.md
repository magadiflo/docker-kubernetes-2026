## 🚀 Guía de Arranque: Levantando la Infraestructura Completa desde Cero

Esta guía sirve como referencia rápida para levantar todo el proyecto desde cero — útil si retomas el proyecto después
de un tiempo sin tocarlo, o si necesitas reconstruir el entorno en una máquina nueva.

### 📝 Orden de Ejecución

1. **✅ Prerrequisitos** — Docker Desktop, Minikube y `kubectl` instalados y funcionando.

2. **🐳 Build + push de imágenes a Docker Hub** — construir y subir las imágenes actualizadas de cada microservicio
   (`authorization-server`, `gateway-server`, `user-service`, `course-service`, `courses-app`).

3. **▶️ Iniciar Minikube** — levantar el clúster local.
   ```bash
   minikube start
   ```

4. **💾 Volúmenes (`PV` + `PVC`)** — deben aplicarse primero, ya que MySQL y PostgreSQL dependen de ellos para persistir
   datos.

   > 💡 **¿El orden entre `PV` y `PVC` importa?** Kubernetes es tolerante en este punto: si aplicas primero el
   > `PVC`, simplemente queda en estado `Pending` hasta que aparezca un `PV` compatible que lo satisfaga, y en
   > cuanto ese `PV` se crea, ambos se enlazan (*bind*) automáticamente. Dicho esto, la práctica recomendada —y la
   > que seguimos aquí— es **aplicar primero el `PV`**, ya que evita ese estado intermedio de espera y hace el
   > proceso más predecible y fácil de seguir en una guía como esta.

5. **🔐 Secrets** — aplicarlos antes que los `Deployment`s, ya que estos últimos los referencian vía
   `secretKeyRef`.

6. **🌐 Services** — aplicarlos temprano para tener disponibles los `CLUSTER-IP` (necesarios en el paso 7).

7. **📌 Obtener la `CLUSTER-IP` de `svc-authorization-server` y actualizar los `hostAliases`** — como esta IP se asigna
   dinámicamente y **cambia cada vez que se recrea el `Service`** (por ejemplo, tras un `minikube delete`), es
   indispensable consultarla con `kubectl get services` y actualizar manualmente el bloque `hostAliases` en los
   `Deployment`s de `d-gateway-server`, `d-course-service` y `d-user-service` **antes** de aplicarlos. Si se omite este
   paso, esos tres Pods fallarán al intentar resolver `auth.magadiflo.local`, reproduciendo el error
   `Connection refused` documentado en la primera entrega de esta serie.

8. **🗄️ Deployments de bases de datos** (MySQL, PostgreSQL) — deben estar listas antes que los microservicios que las
   consultan.

9. **⚙️ ConfigMaps** — ya con las URLs definitivas (`auth.magadiflo.local`, `gateway.magadiflo.local`,
   `courses.magadiflo.local`).

10. **🔓 Elevación de permisos mediante RBAC** *(ver `17.kubernetes_spring_cloud.md`)*

    Nuestros microservicios usan `spring-cloud-starter-kubernetes-client`, una librería que permite a la aplicación
    **listar y observar (watch) los `Services`/`Endpoints` del clúster** en tiempo real, a través del API Server de
    Kubernetes — esto es lo que le permite a Spring Cloud hacer *service discovery* nativo, sin depender de un servidor
    de registro externo como Eureka.

    El problema es que, por defecto, cuando Kubernetes levanta un Pod en el namespace `default`, le asigna
    automáticamente una identidad llamada `ServiceAccount: default`. Por motivos de seguridad, esta cuenta viene
    **completamente restringida** de fábrica: no tiene permisos para listar, observar (`watch`) ni leer ningún recurso a
    través del API Server. Cuando la librería de Spring intenta iniciar su *Informer* (el componente interno que
    mantiene sincronizada la lista de `Services`/`Endpoints`), el API Server responde con un `403
    Forbidden`, y esa falla detiene por completo el arranque del servidor Tomcat embebido.

    Para solucionar esto, usamos el control de acceso basado en roles de Kubernetes (**RBAC**), otorgándole al
    `ServiceAccount` por defecto del namespace los permisos necesarios:

    ```bash
    kubectl create clusterrolebinding admin --clusterrole=cluster-admin --serviceaccount=default:default
    ```

    > ⚠️ **Nota de seguridad:** este comando otorga el rol `cluster-admin` — el más permisivo que existe en Kubernetes —
    al `ServiceAccount` por defecto. Es una solución rápida y suficiente para un entorno de **desarrollo local en
    Minikube**, pero **no es una práctica recomendable en un clúster de producción real**, donde lo correcto sería crear
    un `Role`/`ClusterRole` **específico**, limitado únicamente a los verbos (`list`, `watch`, `get`) y recursos
    (`services`, `endpoints`) que Spring Cloud Kubernetes realmente necesita, en lugar de administrador total del
    clúster.

    > ⚠️ **Importante — no olvidar este paso al reconstruir el clúster:** este `ClusterRoleBinding` es un objeto de
    Kubernetes como cualquier otro — al ejecutar `minikube delete`, se elimina junto con todo lo demás, y al levantar el
    clúster nuevamente desde cero, este permiso simplemente no existe hasta que lo volvamos a aplicar. Como no forma
    parte de ningún archivo `.yml` versionado en el proyecto (se crea con un comando imperativo directo, no con
    `kubectl apply -f`), es un paso fácil de olvidar si no está documentado explícitamente. Por eso queda registrado
    aquí, como parte obligatoria de esta guía.

11. **📦 Deployments del resto de microservicios** — `user-service`, `course-service`, `gateway-server` (estos tres ya
    deberían estar con los `hostAliases` actualizados del paso 7), `authorization-server` y `courses-app`.

12. **🚇 `minikube tunnel`** — dejarlo corriendo en su propia terminal.

13. **📄 Archivo `hosts` de Windows** — agregar las entradas de `auth.magadiflo.local`, `gateway.magadiflo.local`
    y `courses.magadiflo.local` apuntando a `127.0.0.1`.

14. **⏳ Esperar a que todos los Pods entren en funcionamiento**

    Los Pods no quedan listos de forma instantánea — es normal que tome unos minutos mientras las imágenes se descargan
    (si no estaban cacheadas localmente), las aplicaciones Spring Boot arrancan, y los `readinessProbe`
    configurados confirman que cada instancia está realmente lista para recibir tráfico.

    Puedes monitorear el progreso de dos formas:

    ```bash
    # Ver el estado general de todos los Pods, columna READY
    kubectl get pods

    # Ver los logs de un Pod específico
    kubectl logs <nombre-del-pod>
    ```

    > 📊 **Referencia de tiempos:** en una prueba real, el Pod que más demoró en quedar listo fue `user-service`
    (~10 minutos aproximadamente) — probablemente debido a que corre con **3 réplicas**, cada una debiendo completar su
    propio arranque, `readinessProbe` y registro de discovery de forma independiente. Los demás microservicios (con una
    sola réplica) suelen quedar listos considerablemente más rápido. Estos tiempos son solo una referencia; pueden
    variar según los recursos de tu máquina.

15. **🔎 Verificación final** — ingresar a `http://courses.magadiflo.local:8080` y confirmar que todo funcione
    correctamente (catálogo de cursos visible, login funcional, operaciones autenticadas disponibles).

> 💡 **Nota adicional para el futuro:** el paso manual 7 (actualizar la `CLUSTER-IP` en los `hostAliases`) es exactamente
> el tipo de fricción que la implementación con **Ingress** elimina — ahí, en vez de depender de una `CLUSTER-IP` que
> cambia en cada reconstrucción del clúster, todos los `hostAliases` apuntan a la IP estable del Ingress Controller,
> reduciendo considerablemente el mantenimiento manual necesario cada vez que se reinicia el clúster desde cero.
