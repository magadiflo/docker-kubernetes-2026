# 🌐 Sección 18: Kubernetes — Spring Cloud Gateway

## 🚪 Introducción

El crecimiento de una arquitectura de microservicios introduce la necesidad de centralizar el tráfico entrante. Exponer
IPs individuales de servicios o depender de múltiples balanceadores externos es inviable en entornos corporativos.
En esta sección aprenderemos a crear y configurar un **API Gateway** utilizando `Spring Cloud Gateway` dentro de un
entorno Kubernetes.

### 🗺️ Arquitectura Conceptual del Tráfico

El `API Gateway` cumple un rol fundamental en una arquitectura de microservicios, ya que actúa como el **punto de
entrada único** para todos los clientes externos (Web, Mobile, Terceros).

````
                 ▲ [ Tráfico Externo HTTP/REST ]
                 │
      ┌──────────┴──────────┐
      │  Spring Cloud       │ ◄─── Consulta al API Server de K8s
      │  Gateway Server     │      (Service Discovery Dinámico)
      └────┬───────────┬────┘
           │           │
           ▼           ▼
┌─────────────────┐ ┌───────────────────┐
│ svc-user-service│ │ svc-course-service│
│ (Pods de Users) │ │ (Pods de Courses) │
└─────────────────┘ └───────────────────┘
````

### 📊 Responsabilidades Clave del Gateway

| **Función**                    | **Descripción Mecánica**                                                                                                                                                                                                                                                                                                                                                                                             | **Beneficio Operacional**                                                                                                                                            |
|--------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 🔀 **Enrutamiento Dinámico**   | Intercepta la URL entrante (ej.: `/api/v1/users/**`) y la redirige al Service de Kubernetes correspondiente.                                                                                                                                                                                                                                                                                                         | Los clientes externos solo conocen un único Host y Puerto. No necesitan conocer la ubicación real de cada microservicio, sino que solo interactúan con el `Gateway`. |
| 🔍 **Descubrimiento Nativo**   | Utiliza las APIs de Kubernetes para listar y rastrear los Pods activos detrás de un Service, sin necesidad de Netflix Eureka.                                                                                                                                                                                                                                                                                        | Desacoplamiento total y sincronización automática ante eventos de autoescalado.                                                                                      |
| ⚖️ **Balanceo de Carga**       | Distribuye las solicitudes de manera equitativa entre todas las réplicas saludables del microservicio de destino.                                                                                                                                                                                                                                                                                                    | Alta disponibilidad y mejor aprovechamiento de los recursos de hardware.                                                                                             |
| 🛡️ **Cross-Cutting Concerns** | Centraliza funcionalidades transversales que deben aplicarse de forma uniforme a todas las solicitudes, como autenticación, autorización, validación de tokens (JWT/OAuth2), logging, métricas, trazabilidad (*tracing*), limitación de tasa (*Rate Limiting*), políticas CORS, reescritura de rutas, manipulación de cabeceras HTTP, filtros globales y políticas de resiliencia (como *Retry* o *Circuit Breaker*) | Evita duplicar lógica transversal en cada microservicio.                                                                                                             |

## 🛠️ Creando el Microservicio `gateway-server`

Generamos un nuevo proyecto
desde [Spring Initializr](https://start.spring.io/#!type=maven-project&language=java&platformVersion=4.0.7&packaging=jar&configurationFileFormat=yaml&jvmVersion=25&groupId=dev.magadiflo&artifactId=gateway-server&packageName=dev.magadiflo.gateway.app&dependencies=lombok,actuator,cloud-gateway-reactive),
con la siguiente configuración base:

### 📦 Dependencias en `pom.xml`

````xml
<!--Spring Boot 4.0.7-->
<!--spring-cloud.version 2025.1.2-->
<!--Java 25-->
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-gateway-server-webflux</artifactId>
    </dependency>

    <!--Agregado manualmente-->
    <!-- Cliente de Kubernetes para descubrimiento de servicios -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-kubernetes-client</artifactId>
    </dependency>
    <!-- Balanceador de carga basado en el cliente de Kubernetes -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-kubernetes-client-loadbalancer</artifactId>
    </dependency>
    <!--/Agregado manualmente-->
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator-test</artifactId>
        <scope>test</scope>
    </dependency>
    <dependency>
        <groupId>io.projectreactor</groupId>
        <artifactId>reactor-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
````

### 🔍 ¿Por qué estas dependencias?

| Dependencia                                           | Motivo                                                                                                     |
|-------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `spring-cloud-starter-gateway-server-webflux`         | Motor principal del Gateway. Usa WebFlux (reactivo) para manejar peticiones de forma no bloqueante.        |
| `spring-cloud-starter-kubernetes-client`              | Permite al Gateway descubrir los servicios disponibles en el clúster usando la API de Kubernetes.          |
| `spring-cloud-starter-kubernetes-client-loadbalancer` | Habilita el balanceo de carga del lado del cliente (`@LoadBalanced`) hacia los Pods de los microservicios. |
| `spring-boot-starter-actuator`                        | Expone endpoints de monitoreo y salud del Gateway.                                                         |

> 🧠 **Nota de Ingeniería:**  
> A diferencia de los despliegues tradicionales en servidores locales donde se suele inyectar `Netflix Eureka Server`,
> aquí delegamos esa tarea por completo a `Kubernetes`. Las dependencias `kubernetes-client` permiten que
> `Spring Boot` interrogue al `Control Plane` del clúster para resolver los nombres de red de nuestros microservicios
> en tiempo real.

## 🛠️ Configuración Base del Microservicio `gateway-server`

Con las dependencias asentadas en el proyecto, procederemos a habilitar el motor de descubrimiento en el código fuente
Java y a establecer las propiedades de entorno iniciales en el manifiesto de configuración de Spring Boot.

### El Rol de `@EnableDiscoveryClient` (Análisis Técnico)

Inyectamos de forma declarativa la anotación de descubrimiento en nuestra clase conductora principal:

````java

@EnableDiscoveryClient // 💡 Opcional/Declarativo en versiones modernas
@SpringBootApplication
public class GatewayServerApplication {

    public static void main(String[] args) {
        SpringApplication.run(GatewayServerApplication.class, args);
    }

}
````

> 🧠 **Nota de Arquitectura Desmitificada:**  
> Técnicamente hablando, en las versiones modernas de `Spring Cloud`, la anotación `@EnableDiscoveryClient`
> ya no es estrictamente obligatoria. El simple hecho de haber inyectado el artefacto
> `spring-cloud-starter-kubernetes-client` en el `pom.xml` gatilla la auto-configuración automática del
> `DiscoveryClient` durante el arranque de la JVM.
>
> Mantener la anotación en el código opera más como una buena práctica documental y explícita
> (para que cualquier desarrollador que lea el código entienda de inmediato el rol de este servidor)
> que como un requerimiento técnico estricto de compilación.

### Configuración del Archivo `application.yml`

Definimos el archivo de propiedades iniciales de la aplicación. Mapearemos un puerto por defecto alto (`8090`)
tradicionalmente usado para balanceadores y proxies de desarrollo, asegurando la exposición completa de mensajes
de error de Actuator:

````yml
server:
  port: ${CONTAINER_PORT:8090}
  error:
    include-message: always

spring:
  application:
    name: gateway-server
````

- `server.port`: Establece el puerto nativo de escucha del servidor embebido Netty. Utiliza la sintaxis de interpolación
  para buscar la variable de entorno `CONTAINER_PORT` (la cual inyectaremos más adelante mediante un `ConfigMap` de
  Kubernetes), usando `8090` como fallback local de desarrollo.
- `server.error.include-message: always`: Configuración clave para etapas de desarrollo. Fuerza a Spring Boot WebFlux a
  enviar el detalle textual de los errores HTTP en el cuerpo de la respuesta JSON, facilitando el debugging al rastrear
  fallas de enrutamiento.
- `spring.application.name`: Define el identificador interno del microservicio para el ecosistema de Spring.
  En Kubernetes, este valor es clave por convención, ya que `Spring Cloud Kubernetes` lo utilizará **por defecto**
  para buscar e inyectar automáticamente los `ConfigMaps` o `Secrets` que tengan este mismo nombre (`gateway-server`),
  facilitando la configuración centralizada. (**Nota:** Esto ocurre siempre y cuando no se defina explícitamente otro
  nombre de recurso en las propiedades de Spring; si se cambia la ruta o nombre del `ConfigMap/Secret` en
  la configuración, esta convención ya no aplica. Asimismo, cabe recordar que la identidad de red oficial
  dentro del clúster la definirá el objeto `Service` de Kubernetes que crearemos más adelante).

## 🗺️ Configurando las Rutas de los Microservicios en el Gateway

El corazón del `API Gateway` es la definición de rutas — las reglas que determinan hacia qué microservicio se redirige
cada petición entrante. Actualizamos el `application.yml` con la configuración de enrutamiento:

````yml
server:
  port: ${CONTAINER_PORT:8090}
  error:
    include-message: always

spring:
  application:
    name: gateway-server

  # 🌐 Orquestación de Rutas Reactivas
  cloud:
    gateway:
      routes:
        # 📚 Ruta hacia el Microservicio de Cursos
        - id: course-service-route
          uri: lb://svc-course-service
          predicates:
            - Path=/api/v1/courses/**

        # 👥 Ruta hacia el Microservicio de Usuarios
        - id: user-service-route
          uri: lb://svc-user-service
          predicates:
            - Path=/api/v1/users/**
````

### 🔍 Explicación de los campos clave

#### 🆔 `id`

Identificador único de la ruta dentro del Gateway. Solo se usa como referencia interna para administración y debugging
— no afecta el enrutamiento.

#### 🔗 `uri`

Define el destino al que el Gateway redirigirá la solicitud.

| Componente                      | Descripción                                                                                                                                                                   |
|---------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Prefijo `lb://` (Load Balancer) | Indica que se usará `Spring Cloud LoadBalancer` junto con `Kubernetes Service Discovery` para balancear las peticiones entre los Pods disponibles.                            |
| Nombre tras `lb://`             | Debe coincidir **exactamente** con el nombre del `Service` de Kubernetes, ya que es este objeto el que expone los Pods y permite resolverlos mediante DNS dentro del clúster. |

🎯 **Mecánica Interna:** Al configurarse como `lb://svc-user-service`, el Gateway interroga al `API Server` de
Kubernetes, obtiene la lista de IPs privadas de los Pods asociados a ese `Service` y balancea dinámicamente
el tráfico entre ellos utilizando algoritmos eficientes (como `Round Robin`).

#### 🔀 `predicates` (Predicados)

Son las condiciones que debe cumplir una solicitud entrante para que se aplique la ruta.
El predicado más común es `Path`, que filtra según la URL:

| Predicado                 | Destino                                                                                     |
|---------------------------|---------------------------------------------------------------------------------------------|
| `Path=/api/v1/courses/**` | Todo el tráfico con esa ruta se redirige al microservicio de cursos (`svc-course-service`). |
| `Path=/api/v1/users/**`   | Todo el tráfico con esa ruta se redirige al microservicio de usuarios (`svc-user-service`). |

> ⚡ Con esta configuración, los clientes externos solo necesitan conocer la dirección del
> Gateway — ya no es necesario exponer cada microservicio individualmente. El Gateway actúa
> como la única puerta de entrada al sistema.

### 🌊 El Ciclo de Vida de una Petición a través del Gateway

Para visualizar el desacoplamiento total que acabamos de implementar, el flujo del cliente opera bajo esta secuencia:

````
[Cliente Externo] 
       │ (Solo conoce la IP:Puerto del Gateway)
       ▼
`GET http://<gateway>/api/v1/users/info`
       │
       ├──► [Gateway Server]: Evalúa predicado Path=/api/v1/users/** (¡Match!)
       ├──► [Kubernetes Discovery]: Resuelve `lb://svc-user-service` a IPs de Pods activos.
       │
       ▼
[Pod Saludable: 10.244.1.51:8001] (El cliente externo nunca se enteró de esta IP interna)
````

## 🐳 Creando la Imagen Docker del `gateway-server`

Para desplegar el `Spring Cloud Gateway` en Kubernetes, primero necesitamos dockerizar la aplicación. Aprovecharemos la
misma estructura de `Dockerfile` multi-stage que usamos en los otros microservicios, con una única modificación: el
puerto expuesto cambia a `8090`.

````dockerfile
FROM eclipse-temurin:25-jdk-alpine AS dependencies
WORKDIR /app
COPY ./mvnw ./
COPY ./.mvn ./.mvn
COPY ./pom.xml ./
RUN sed -i -e 's/\r$//' ./mvnw && ./mvnw dependency:go-offline
COPY ./src ./src
RUN ./mvnw clean package -DskipTests

FROM eclipse-temurin:25-jre-alpine AS builder
WORKDIR /app
COPY --from=dependencies /app/target/*.jar ./app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:25-jre-alpine AS runner
WORKDIR /app
RUN mkdir ./logs
COPY --from=builder /app/dependencies ./
COPY --from=builder /app/spring-boot-loader ./
COPY --from=builder /app/snapshot-dependencies ./
COPY --from=builder /app/application ./
EXPOSE 8090
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
````

> 📌 **Antes de construir la imagen**, es necesario crear un nuevo repositorio en `Docker Hub` para alojar la imagen
> del `gateway-server`.
