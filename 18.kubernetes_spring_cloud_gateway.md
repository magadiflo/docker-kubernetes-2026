# 🌐 Sección 18: Kubernetes — Spring Cloud Gateway

## 🚪 Introducción

El crecimiento de una arquitectura de microservicios introduce la necesidad de centralizar el tráfico entrante. Exponer
IPs individuales de servicios o depender de múltiples balanceadores externos es inviable en entornos corporativos.
En esta sección aprenderemos a crear y configurar un **API Gateway** utilizando `Spring Cloud Gateway` dentro de un
entorno Kubernetes.

### 🗺️ Arquitectura Conceptual del Tráfico

El `API Gateway` cumple un rol fundamental en una arquitectura de microservicios, ya que actúa como el **punto de
entrada único** para todos los clientes externos (Web, Mobile, Terceros).

````
                 ▲ [ Tráfico Externo HTTP/REST ]
                 │
      ┌──────────┴──────────┐
      │  Spring Cloud       │ ◄─── Consulta al API Server de K8s
      │  Gateway Server     │      (Service Discovery Dinámico)
      └────┬───────────┬────┘
           │           │
           ▼           ▼
┌─────────────────┐ ┌───────────────────┐
│ svc-user-service│ │ svc-course-service│
│ (Pods de Users) │ │ (Pods de Courses) │
└─────────────────┘ └───────────────────┘
````

### 📊 Responsabilidades Clave del Gateway

| **Función**                    | **Descripción Mecánica**                                                                                                                                                                                                                                                                                                                                                                                             | **Beneficio Operacional**                                                                                                                                            |
|--------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 🔀 **Enrutamiento Dinámico**   | Intercepta la URL entrante (ej.: `/api/v1/users/**`) y la redirige al Service de Kubernetes correspondiente.                                                                                                                                                                                                                                                                                                         | Los clientes externos solo conocen un único Host y Puerto. No necesitan conocer la ubicación real de cada microservicio, sino que solo interactúan con el `Gateway`. |
| 🔍 **Descubrimiento Nativo**   | Utiliza las APIs de Kubernetes para listar y rastrear los Pods activos detrás de un Service, sin necesidad de Netflix Eureka.                                                                                                                                                                                                                                                                                        | Desacoplamiento total y sincronización automática ante eventos de autoescalado.                                                                                      |
| ⚖️ **Balanceo de Carga**       | Distribuye las solicitudes de manera equitativa entre todas las réplicas saludables del microservicio de destino.                                                                                                                                                                                                                                                                                                    | Alta disponibilidad y mejor aprovechamiento de los recursos de hardware.                                                                                             |
| 🛡️ **Cross-Cutting Concerns** | Centraliza funcionalidades transversales que deben aplicarse de forma uniforme a todas las solicitudes, como autenticación, autorización, validación de tokens (JWT/OAuth2), logging, métricas, trazabilidad (*tracing*), limitación de tasa (*Rate Limiting*), políticas CORS, reescritura de rutas, manipulación de cabeceras HTTP, filtros globales y políticas de resiliencia (como *Retry* o *Circuit Breaker*) | Evita duplicar lógica transversal en cada microservicio.                                                                                                             |

## 🛠️ Creando el Microservicio `gateway-server`

Generamos un nuevo proyecto
desde [Spring Initializr](https://start.spring.io/#!type=maven-project&language=java&platformVersion=4.0.7&packaging=jar&configurationFileFormat=yaml&jvmVersion=25&groupId=dev.magadiflo&artifactId=gateway-server&packageName=dev.magadiflo.gateway.app&dependencies=lombok,actuator,cloud-gateway-reactive),
con la siguiente configuración base:

### 📦 Dependencias en `pom.xml`

````xml
<!--Spring Boot 4.0.7-->
<!--spring-cloud.version 2025.1.2-->
<!--Java 25-->
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-gateway-server-webflux</artifactId>
    </dependency>

    <!--Agregado manualmente-->
    <!-- Cliente de Kubernetes para descubrimiento de servicios -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-kubernetes-client</artifactId>
    </dependency>
    <!-- Balanceador de carga basado en el cliente de Kubernetes -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-kubernetes-client-loadbalancer</artifactId>
    </dependency>
    <!--/Agregado manualmente-->
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-actuator-test</artifactId>
        <scope>test</scope>
    </dependency>
    <dependency>
        <groupId>io.projectreactor</groupId>
        <artifactId>reactor-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
````

### 🔍 ¿Por qué estas dependencias?

| Dependencia                                           | Motivo                                                                                                     |
|-------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `spring-cloud-starter-gateway-server-webflux`         | Motor principal del Gateway. Usa WebFlux (reactivo) para manejar peticiones de forma no bloqueante.        |
| `spring-cloud-starter-kubernetes-client`              | Permite al Gateway descubrir los servicios disponibles en el clúster usando la API de Kubernetes.          |
| `spring-cloud-starter-kubernetes-client-loadbalancer` | Habilita el balanceo de carga del lado del cliente (`@LoadBalanced`) hacia los Pods de los microservicios. |
| `spring-boot-starter-actuator`                        | Expone endpoints de monitoreo y salud del Gateway.                                                         |

> 🧠 **Nota de Ingeniería:**  
> A diferencia de los despliegues tradicionales en servidores locales donde se suele inyectar `Netflix Eureka Server`,
> aquí delegamos esa tarea por completo a `Kubernetes`. Las dependencias `kubernetes-client` permiten que
> `Spring Boot` interrogue al `Control Plane` del clúster para resolver los nombres de red de nuestros microservicios
> en tiempo real.
